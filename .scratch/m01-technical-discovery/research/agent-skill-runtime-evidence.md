# Agent Skill runtime evidence for M01

Investigated: **2026-10-18**. Purpose: factual prerequisites for [Establish Agent Skill runtime capabilities and constraints](../issues/01-agent-skill-runtime-evidence.md), under [Technical Discovery for M01 — Content Production](../map.md). This is research evidence, not an orchestration decision or implementation specification.

## Evidence boundaries

- **Documented** means a current official page explicitly describes the capability. It is a documentation claim, not an unconditional service or correctness guarantee.
- **Observed** means a safe read, CLI help/version probe, or tool interaction in this discovery session. It establishes availability here, not portability to another client/account or successful production execution.
- **Inference / unresolved** identifies consequences for M01 or an assumption the investigation did not establish.

Official documentation was retrieved on the investigation date. Older `developers.openai.com/codex/...` pages redirected to `learn.chatgpt.com/docs/...`; citations below use their resulting official URLs. Context7 was resolved first with “OpenAI Codex”; `/openai/codex` was selected for exact product relevance and first-party provenance. Three concept-scoped queries covered skills discovery, long work/resume, and subagent boundaries. Context7 returned first-party repository snippets, which were used as leads; the factual matrix cites fetched official product pages rather than assuming repository `main` matches the installed release.

No course material, credentials, account history, or full configuration was accessed. No additional prompt-bearing CLI/API run or production capability test was started, and no production skill was executed. No runtime settings were changed. The small local probes below cannot establish model quality, context endurance, or recovery after a crash.

## Documented capabilities

| Area | Documented fact | Limit relevant to later decisions |
| --- | --- | --- |
| Skill format and discovery | A skill has `SKILL.md` with `name` and `description`; scripts, references, and assets are optional. Codex scans `.agents/skills` between the current directory and repository root, plus user/admin/system roots. Duplicate names are not merged. [Build skills](https://learn.chatgpt.com/docs/build-skills) | Invocation identity must not assume names are globally unique. |
| Invocation and context loading | Explicit `$` mentions or `/skills` work in CLI/IDE; description matching permits implicit invocation. Metadata loads first; selected instructions load later. The initial catalog normally uses at most 2% of model context, falling back to 8,000 characters when unknown; descriptions may shorten and skills may be omitted. Changes are detected automatically, with restart as fallback. [Build skills](https://learn.chatgpt.com/docs/build-skills) | Large catalogs can affect discoverability; a skill body is not all loaded at session start. |
| Explicit invocation policy | `agents/openai.yaml` supports `policy.allow_implicit_invocation: false`, preserving explicit invocation. [Build skills](https://learn.chatgpt.com/docs/build-skills) | Existing frontmatter keys from another skill system do not establish equivalent enforcement. |
| Inputs and observable outputs | `codex exec` accepts a prompt and piped context; progress goes to stderr and final text to stdout. Forking creates another chat; a managed worktree is available for appropriate new/forked local sessions, not resume. [Developer commands](https://learn.chatgpt.com/docs/developer-commands) | Conversation continuation and filesystem isolation are separate features. [Long-running work](https://learn.chatgpt.com/docs/long-running-work) | Long-work support does not turn automated completion into the user's explicit lesson approval. This investigation started no goal. |
| Tool permissions | Sandbox boundaries govern files/network and spawned commands; approval policy separately governs requests to cross boundaries. [Sandbox](https://learn.chatgpt.com/docs/sandboxing) | A skill instruction cannot itself establish a stronger technical boundary than the running session. |

Interactive approvals can arise from inactive threads; an action needing unavailable fresh approval fails in non-interactive flows. Concurrent writes can conflict. [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents) | Delegation is available, but independent write ownership and approval handling require deliberate workflow treatment. [Model Context Protocol](https://learn.chatgpt.com/docs/extend/mcp) | A skill describing research is not evidence that a named MCP, web tool, credential, network route, or source exists in every runtime. |

## Implications and unsupported assumptions

The following are **inferences from the boundary between the evidence above and the [approved PRD](../../../docs/product/PRD.md)**. They leave later policy choices open.

1. **Independently runnable responsibilities are feasible.** A repository skill can describe one responsibility, read specified repository inputs, and write inspectable results. P18/P24 still need project-defined input validity, outputs, observable completion, failure behavior, and representative cases. No runtime promise supplies those domain contracts automatically.
2. **Native resume is useful but insufficient for P26.** There is no evidence here of automatic immutable Approved Lessons, partial-write rollback, dependency invalidation, stale research detection, or exactly-once stage execution. A recovery decision must state what a fresh session can learn from durable artifacts when chat history is unavailable.
3. **Conversation state is not an approval ledger.** P21 requires an explicit user decision. Tool-execution approval, goal completion, a QA pass, and a successful thread event do not establish that decision. The format and preservation of lesson approval remain open.
4. **Research provenance must outlive tool results.** Retrieval works here, but neither Context7 snippets nor a source URL alone establishes that the intended version was checked. Later decisions must define what source/version/date and claim-to-evidence relationships are retained and when rechecking is required. No retention schema is chosen here.
5. **Delegation does not define the production stages.** A skill, a responsibility, a subagent, a session, and a Git worktree are different mechanisms. The number of skills/roles and whether work is serial, delegated, or manually invoked are unresolved choices. The observed four-slot cap is not a portable product requirement.
6. **Repeatability is not identical regenerated text.** No controlled rerun or model comparison was performed. The evidence establishes no deterministic book generation, zero-error QA, exhaustive source coverage, fixed execution cost, whole-course context fit, guaranteed multi-hour uptime, or cross-client parity.

## Questions now precise enough for downstream decisions

- What minimum input/output and acceptance contract makes one responsibility independently runnable and inspectable?
- Which records preserve input identity, artifact revision, approval, dependencies, and the next action across a fresh session or corrected intermediate result?
- Which permissions and write-ownership rules should invocation/handoff require, and what happens when a tool or fresh approval is unavailable?
- What evidence identifies the technical version being explained, connects an enrichment claim to sources, and triggers rechecking after changes?

These questions already fit the map's workflow, artifact, provenance, and recovery areas; this research does not create or resolve their policy tickets. There is no discovered fact requiring a new orchestration framework, embedded reader AI, whole-course input, or a change to the PRD.
